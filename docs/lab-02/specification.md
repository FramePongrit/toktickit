# Lab 2 Sprint Engineering Specification

**Project:** TokTickIT — IT Support Ticketing System
**Sprint:** Lab 2 — Requester Ticketing MVP with UI Foundation
**Status:** Approved before implementation
**Related documents:** [api-spec.md](./api-spec.md) · [ui-spec.md](./ui-spec.md) · [tests.md](./tests.md)

---

## 1. Sprint Goal

Deliver the Requester-facing half of TokTickIT: a person with an IT problem can describe it, classify it, attach evidence, submit it, and receive an official Ticket Number generated by the backend. They can then find that ticket again in a searchable, filterable, sortable, paginated list of **only their own** tickets, open it, and manage its attachments. Because authentication arrives in Lab 3, a temporary Development Requester Selector supplies the current identity. This sprint also establishes the Zen Green visual language and the reusable form, list, badge, state, and responsive conventions that every later screen will inherit.

---

## 2. Stakeholder Request Interpretation

The stakeholder asked for a "professional and responsive Requester-facing ticketing experience". Reading that against the constraints, we interpret it as four obligations:

1. **The backend owns the truth.** The Ticket Number, the creation timestamp, and the initial status are generated server-side and are never accepted from the client. The screenshots submitted as evidence must show values that demonstrably came from the database.
2. **Ownership is a security property, not a UI filter.** "Prevent one Requester from viewing another Requester's ticket" is satisfied only if the *server* refuses. Hiding a row in the client is not a satisfying implementation of that sentence.
3. **The selector is a stand-in, not a login.** It must be labelled as such in the UI and must not accumulate any of the trappings of authentication (no password field, no session token, no "remember me" security claim). Its only job is to supply an identity for testing multi-user ownership.
4. **"Establish conventions" is a deliverable in itself.** Lab 2 is graded partly on whether Lab 3 can reuse the theme, components, and API conventions rather than reinventing them. Consistency is therefore in scope, not a nice-to-have.

## 3. Scope

### 3.1 Included

- Development Requester Selection screen, selected-requester display in the app shell, and Change Requester
- Create Ticket: form, client and server validation, submission, success state showing the generated Ticket Number
- My Tickets: requester-owned paginated list with search, filters, sorting, and loading / empty / no-results / failure states
- Requester Ticket Detail: read-only ticket information
- Attachment lifecycle: upload, metadata display, download of active attachments, soft removal with a reason
- Backend-enforced ownership on every ticket and attachment operation
- Zen Green theme, reusable components, and the three responsive breakpoints
- Automated tests at unit, API, UI component, UI style, responsive, and end-to-end level
- Data model, migrations, and idempotent seed data

### 3.2 Excluded

- **Authentication and security:** login, logout, passwords, password hashing, sessions, tokens, and real role-based authorization. The Development Requester Selector is explicitly *not* authentication and must not be described as such.
- **IT Staff workflow:** staff dashboard, ticket queue, claiming or reassigning tickets, setting IT Priority, ticket ownership by staff
- **Collaboration:** Public Comments, Internal Notes, Actions Taken
- **Lifecycle beyond creation:** any status change after `NEW` — resolving, closing, reopening, cancelling, resolution confirmation
- **Administration:** managing users, requesters, roles, or reference data through the UI

## 4. Functional Requirements

### Development Requester context

- **FR-01** The system shall present a Development Requester Selection screen listing every **active** Development Requester loaded from PostgreSQL.
- **FR-02** The system shall prevent access to Create Ticket, My Tickets, and Ticket Detail until a Development Requester has been selected, redirecting to the selection screen instead.
- **FR-03** The system shall display the selected Requester's name in the application shell on every screen.
- **FR-04** The system shall provide a Change Requester action that returns the user to the selection screen and reloads all requester-specific data for the new selection.
- **FR-05** The system shall persist the selected Requester across page reloads and revalidate it against the server on load.

### Ticket creation

- **FR-06** The system shall allow the selected Requester to create a Ticket by supplying Category, Related System, Requested Priority, Ticket Summary, and Description.
- **FR-07** The system shall generate a unique official Ticket Number in the backend and display it to the Requester on success.
- **FR-08** The system shall reject invalid Create Ticket submissions and display a validation message next to each offending field.
- **FR-09** The system shall preserve the Requester's entered values when a submission fails for any reason.
- **FR-10** The system shall prevent duplicate submission by disabling the submit control and showing a busy state while a request is in flight.

### My Tickets

- **FR-11** The system shall list only the Tickets owned by the selected Requester.
- **FR-12** The system shall allow searching those Tickets by Ticket Number or Summary.
- **FR-13** The system shall allow filtering those Tickets by Category, Related System, and Requested Priority.
- **FR-14** The system shall allow sorting those Tickets by creation date, Ticket Number, Requested Priority, or Summary, in ascending or descending order.
- **FR-15** The system shall paginate the Ticket list and report the current page, page size, total count, and total pages.
- **FR-16** The system shall distinguish an empty list (the Requester has no Tickets) from a no-results state (filters matched nothing), and shall offer a Clear Filters action in the latter.
- **FR-17** The system shall allow the Requester to open any listed Ticket's detail screen.

### Ticket Detail

- **FR-18** The system shall display the Ticket's information as read-only: Ticket Number, Ticket Date, Requester, Category, Related System, Ticket Summary, Requested Priority, Description, and Current Status.
- **FR-19** The system shall refuse to return a Ticket that the selected Requester does not own.

### Attachments

- **FR-20** The system shall allow the Requester to attach a permitted file to a Ticket they own.
- **FR-21** The system shall list all Attachments of a Ticket with their filename, type, size, and upload time.
- **FR-22** The system shall allow the Requester to download an active Attachment of a Ticket they own.
- **FR-23** The system shall allow the Requester to soft-remove an Attachment of a Ticket they own, requiring a removal reason.
- **FR-24** The system shall continue to display a removed Attachment as metadata while refusing to serve its content.

### Cross-cutting

- **FR-25** The system shall show an explicit loading state for every asynchronous operation.
- **FR-26** The system shall show a safe error state, revealing no internal details, when a request fails, and shall offer a retry where retrying is meaningful.
- **FR-27** The system shall render every screen usably at desktop, tablet, and mobile widths without horizontal page scrolling.

## 5. Business Rules

### Ticket defaults and system-generated values

- **BR-01** The official Ticket Number is generated by the backend and must be unique. Its format is `TKT-<YYYY>-<NNNNNN>` where `<YYYY>` is the four-digit creation year and `<NNNNNN>` is a zero-padded six-digit sequence that restarts at `000001` each calendar year.
- **BR-02** A new Ticket begins with Current Status `NEW`.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04** Ticket Number, Ticket Date, Requester, and Current Status are system-generated. The client may never supply them; any such value in a request body is ignored.
- **BR-05** Ticket Number allocation must remain unique under concurrent creation. Two Tickets created at the same instant must receive two different numbers.

### Requester selection and switching

- **BR-06** Only Development Requesters with `active = true` may be selected. Inactive Requesters must not appear in the selector.
- **BR-07** If the stored Requester selection no longer refers to an active Requester, the selection is discarded and the user is returned to the selection screen.
- **BR-08** Switching Requester discards all requester-specific data currently on screen and reloads it for the new identity. No data from the previous Requester may remain visible.
- **BR-09** If no active Development Requesters exist, the selector shows an empty state explaining that seed data is missing, and the Continue action is disabled.

### Ticket ownership

- **BR-10** A Ticket belongs to exactly one Requester, fixed at creation from the selected identity. It cannot be reassigned in Lab 2.
- **BR-11** Ownership is enforced in the backend on every read of a Ticket or Attachment. A client-side filter is not sufficient.
- **BR-12** A request for a Ticket or Attachment that the caller does not own returns the same response as a request for one that does not exist. See [BR-13].
- **BR-13** Ownership failures return **404 Not Found**, not 403 Forbidden. A 403 would confirm that the resource exists, letting one Requester enumerate identifiers to map another Requester's data. 404 discloses nothing.

### Search, filtering, sorting, and pagination

- **BR-14** Search matches the query as a case-insensitive substring of either the Ticket Number or the Summary.
- **BR-15** Filters combine conjunctively: a Ticket must satisfy every supplied filter to appear.
- **BR-16** The ownership constraint is applied before and independently of every filter. `requesterId` is never accepted as a query parameter.
- **BR-17** The default sort is creation date descending — newest first.
- **BR-18** Every sort has `id` descending appended as a secondary key, so that pagination remains stable when the primary sort values tie. Without this, one Ticket can appear on two pages and another on none.
- **BR-19** Pages are numbered from 1. The permitted page sizes are 10, 20, and 50; the default is 10.
- **BR-20** An invalid query parameter is rejected with 400 and a field-level message. Invalid values are never silently corrected or clamped, because silent correction cannot be verified by a test.

### Validation and duplicate-submission prevention

- **BR-21** Ticket Summary is required, trimmed before validation and storage, and must be 5–200 characters. The lower bound rejects placeholder input such as "help"; the upper bound keeps the value readable in a single list column.
- **BR-22** Description is required, trimmed, and must be 10–5000 characters. The lower bound forces at least a sentence of context; the upper bound is generous enough for a pasted log excerpt while bounding the payload.
- **BR-23** Category, Related System, and Requested Priority are required. Category and Related System must reference rows that exist and are `active`; a reference to an unknown or inactive row is a **validation failure (400)**, not a missing resource (404), because the fault is in the submitted field value.
- **BR-24** Every rule in BR-21 through BR-23 is enforced on the server. Client-side validation exists only to give faster feedback and is never the sole gate.
- **BR-25** While a Create Ticket request is in flight the submit control is disabled and shows a busy state, so a double click cannot produce two Tickets.

### Failure behaviour and data retained after errors

- **BR-26** A failed submission never clears the form. Every value the Requester entered remains editable so they can retry.
- **BR-27** Error messages shown to the Requester never expose stack traces, SQL, file paths, or internal identifiers.
- **BR-28** Field-level validation errors appear next to their field. A single summary error at the top of the form is not an acceptable substitute, though a summary may accompany the field messages.

### Attachments

- **BR-29** Permitted attachment types are JPG/JPEG, PNG, WEBP, and PDF. Both the file extension and the declared MIME type must be permitted; either one failing rejects the upload. Magic-byte content inspection is out of scope for Lab 2 and is recorded as a known limitation.
- **BR-30** The maximum size is 5 MB per file.
- **BR-31** A Ticket may have at most 5 **active** Attachments. Removed Attachments do not count toward the limit, so a Requester who removes one may upload another.
- **BR-32** Attachment removal is soft. The metadata row is retained and marked removed; the record is never deleted.
- **BR-33** A removed Attachment remains visible as metadata but cannot be downloaded or previewed. A download request for one returns **410 Gone**.
- **BR-34** Removal requires a reason of 3–200 characters. The reason is stored with the identity of the remover and the removal time.
- **BR-35** Removing an already-removed Attachment is a conflict (409), not a silent success, so that a double submission is visible rather than hidden.
- **BR-36** Stored filenames are generated server-side as a random UUID plus the lowercased original extension. The Requester's filename is stored only as display metadata and is never used to build a path, preventing path traversal.
- **BR-37** Uploaded files are never served from a static directory. Every read passes through the ownership-checked download endpoint.
- **BR-38** Only the owner of the parent Ticket may upload to it, download from it, or remove its Attachments.
- **BR-39** If a Ticket is created successfully but a subsequent attachment upload fails, the Ticket is retained. Attachment upload is a separate operation from ticket creation and is never rolled back into it; the Requester is told the Ticket was created and which attachment failed, and may retry the upload from the Ticket Detail screen.
- **BR-40** If an upload is rejected after the file has reached disk, the orphaned file is deleted before the error response is returned.

### Empty and no-results states

- **BR-41** An empty list (the Requester has never created a Ticket) invites the Requester to create their first Ticket.
- **BR-42** A no-results state (filters or search matched nothing) states that the current filters matched nothing and offers Clear Filters. It must not suggest the Requester has no Tickets.
- **BR-43** A Ticket with no Attachments shows an explicit "no attachments" message rather than an empty region.

### Ticket Detail access

- **BR-44** Ticket Detail is read-only in Lab 2. No ticket field may be edited from this screen.
- **BR-45** Ticket Detail must not display Public Comments, Internal Notes, Actions Taken, IT Priority, Ticket Owner, or any status-workflow control, as these belong to later sprints.
- **BR-46** Requesting Ticket Detail without a selected Requester redirects to the Development Requester Selection screen.

### Transition to real authentication in Lab 3

- **BR-47** The Requester identity travels in a single HTTP header, `X-Requester-Id`, resolved by exactly one Express middleware. Lab 3 replaces the contents of that middleware with token verification; no route handler changes.
- **BR-48** No route handler may read the requester identity from anywhere other than the value the middleware attaches to the request.
- **BR-49** The `RequesterUser` model carries a nullable `passwordHash` and a `role` field from Lab 2 onward, so that Lab 3 adds authentication to the existing identity table rather than migrating to a new one.

## 6. UI Specification Summary

Full detail — colour tokens, component states, breakpoint behaviour, accessibility rules, and the visual inspection checklist — is in **[ui-spec.md](./ui-spec.md)**. Summary:

**Application shell.** Zen Green header carrying the TokTickIT identity, primary navigation (My Tickets, Create Ticket), the selected Requester's name, and a Change Requester action. The active page is indicated by more than colour alone. Navigation collapses to a touch-friendly menu below 768 px.

**Development Requester Selection.** A single centred card: title, an explanation that this is a Lab 2 testing mechanism and not a login screen, a dropdown of active Requesters loaded from PostgreSQL, and a Continue action. It has loading, empty, and API-failure states, and all controls are keyboard accessible.

**Create Ticket.** System-generated and read-only values are visually distinct from editable fields. Classification fields (Category, Related System, Requested Priority) are grouped. Summary and Description receive full width. Attachments sit below the main fields. Required fields carry a red asterisk, which never replaces the validation message. Validation messages appear directly below their field in dark red. The submit control shows a busy state and is disabled while submitting. The success state displays the generated Ticket Number with a green confirmation that does not rely on colour alone, plus a link to the new Ticket.

**My Tickets.** A search box, three filters, a sort control, a Clear Filters action, and a Create Ticket action sit above the list. Desktop renders a table; below the `md` breakpoint the same records render as stacked cards, which avoids the horizontal page scroll a table would force. Requested Priority and Current Status render as badges with consistent colour *and* text. Pagination reports the range and total. Loading, empty, no-results, and failure states are all designed, not incidental.

**Ticket Detail.** Read-only ticket fields in soft gray-green shading that is clearly distinct from an editable field but still readable, grouped and responsive. The Attachment section is visually separated from the ticket information and carries its own active, uploading, invalid, and removed states. Removed attachments are greyed with no download affordance and their removal reason shown.

## 7. Data Changes

PostgreSQL via Prisma. Two migrations are applied in order so that no intermediate state is invalid:

1. `add_active_to_category` — adds `active Boolean NOT NULL DEFAULT true` to the existing `Category` table. The default makes the change safe against the already-seeded rows.
2. `lab2_core_models` — adds the enums, the four new models, and all indexes.

### Enums

| Enum | Members | Note |
|---|---|---|
| `Priority` | `LOW`, `MEDIUM`, `HIGH`, `URGENT` | Declared in severity order. PostgreSQL orders enum values by declaration order, so sorting by priority is only meaningful with this ordering. |
| `TicketStatus` | `NEW` | Only member in Lab 2. Later labs append members, which is a non-breaking `ALTER TYPE … ADD VALUE`. |
| `Role` | `REQUESTER`, `STAFF`, `ADMIN` | Present from Lab 2 so Lab 3 does not need an identity migration. |

### Models

| Model | Fields |
|---|---|
| `Category` *(extended)* | `id`, `name @unique`, `active` *(new)*, `createdAt` |
| `RelatedSystem` | `id`, `name @unique`, `active`, `createdAt` |
| `RequesterUser` | `id`, `fullName`, `email @unique`, `department?`, `active`, `role @default(REQUESTER)`, `passwordHash?`, `createdAt`, `updatedAt` |
| `Ticket` | `id`, `ticketNumber @unique`, `requesterId`, `categoryId`, `relatedSystemId`, `requestedPriority`, `summary VarChar(200)`, `description Text`, `currentStatus @default(NEW)`, `createdAt`, `updatedAt` |
| `Attachment` | `id`, `ticketId`, `originalFilename`, `storedFilename @unique`, `mimeType`, `sizeBytes`, `uploadedByRequesterId`, `uploadedAt`, `removedAt?`, `removedByRequesterId?`, `removalReason?` |
| `TicketCounter` | `year @id`, `lastValue @default(0)` |

### Relationships

- One `RequesterUser` owns many `Ticket`s; one `Ticket` belongs to one `RequesterUser`
- One `Ticket` has many `Attachment`s
- One `Category` is used by many `Ticket`s
- One `RelatedSystem` is used by many `Ticket`s
- An `Attachment` additionally records which `RequesterUser` uploaded it and which removed it

Ticket relations to reference data use `onDelete: Restrict` — reference rows must not be deletable while Tickets point at them; deactivate them instead. Attachments use `onDelete: Cascade` from their Ticket.

### Soft removal representation

An Attachment is **active if and only if `removedAt IS NULL`**. A single nullable timestamp is the sole source of truth; there is deliberately no companion boolean, because two representations of one fact can disagree. `removedByRequesterId` and `removalReason` are populated at the same moment and are null while active.

### Indexes

| Index | Justification |
|---|---|
| `Ticket @@index([requesterId, createdAt])` | The My Tickets default query: owner filter plus default sort, served by one index. |
| `Ticket @@index([requesterId, categoryId])` | Owner plus the Category filter facet. |
| `Ticket @@index([requesterId, relatedSystemId])` | Owner plus the Related System filter facet. |
| `Ticket.ticketNumber @unique` | Uniqueness guarantee for BR-01, and the lookup path for search by ticket number. |
| `Attachment @@index([ticketId, removedAt])` | Serves both the active-count check of BR-31 and the detail screen's attachment list. |

Substring search (`q`) uses a case-insensitive `contains`, which is a sequential scan. At the data volumes of this course that is the right trade; a trigram index would be premature. This is recorded as a known limitation rather than treated as a defect.

### Justified design decision — Ticket Number allocation

**Decision:** a dedicated `TicketCounter` table, incremented with `UPDATE … RETURNING` inside the same transaction that inserts the Ticket.

**Alternatives rejected:**

- *`MAX(ticketNumber) + 1`* — two concurrent creates can read the same maximum, so the outcome depends on timing. A unique constraint plus a retry loop can paper over it, but the retry has unbounded worst-case latency and the race is very hard to test deterministically.
- *A PostgreSQL sequence* — gives uniqueness cheaply but cannot restart per calendar year without a scheduled job or a sequence per year, both of which add operational machinery to a student project.

**Why the counter table wins:** `UPDATE "TicketCounter" SET "lastValue" = "lastValue" + 1 WHERE "year" = $1 RETURNING "lastValue"` takes a row lock on that year's row for the duration of the transaction, so concurrent creates serialise on it automatically. Allocation is gap-free, per-year, and needs no retry logic. It is also directly testable: firing N concurrent creates and asserting N distinct numbers passes by construction here, whereas `MAX+1` would pass only by luck. The `@unique` constraint on `ticketNumber` is retained as defence in depth.

**A constraint the database cannot express:** BR-31's "at most 5 active attachments" is a count, not a uniqueness property, so no partial unique index captures it. It is enforced by counting and inserting inside one transaction, and is documented as an application-level invariant rather than a database guarantee.

### Seed data

The seed is idempotent — every row is upserted on its natural key with an empty update clause, so repeated runs never duplicate or mutate. It provides:

- the four required Categories: Account and Access, Hardware, Software, Network
- at least seven Related Systems: Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop
- four **active** Development Requesters
- one **inactive** Development Requester, whose absence from the selector is an acceptance criterion

No Tickets are seeded; tests create their own.

## 8. API Contract

The complete contract — every path, method, request and response shape, status code, error body, and the full ticket-list query contract — is in **[api-spec.md](./api-spec.md)**. Summary of the required capabilities:

| # | Capability | Method and path |
|---|---|---|
| 1 | List active Categories | `GET /api/categories` |
| 2 | List active Related Systems | `GET /api/related-systems` |
| 3 | List active Development Requesters | `GET /api/dev-requesters` |
| 4 | Create a Ticket | `POST /api/tickets` |
| 5 | List the selected Requester's Tickets | `GET /api/tickets` |
| 6 | Retrieve one owned Ticket | `GET /api/tickets/:id` |
| 7 | Upload an Attachment | `POST /api/tickets/:id/attachments` |
| 8 | Retrieve Attachment metadata | `GET /api/attachments/:id` |
| 9 | Download an active Attachment | `GET /api/attachments/:id/download` |
| 10 | Soft-remove an Attachment | `PATCH /api/attachments/:id/remove` |

Conventions that hold across the contract:

- Identity travels in `X-Requester-Id` and is required on `/api/tickets*` and `/api/attachments*`. It is deliberately *not* required on the three reference-data endpoints, because the selection screen must be usable before any Requester is chosen.
- Every non-2xx response uses one shape, `{ "error": { "code", "message", "details"? } }`, produced by a single centralised error handler.
- Reference-data endpoints return bare arrays. `GET /api/tickets` is the only enveloped endpoint, returning `{ data, page, pageSize, total, totalPages }`.
- `GET /api/categories` keeps the exact response shape it had in Lab 1; only its `where` clause changes.

## 9. Acceptance Criteria

### Development Requester context

- **AC-01** Given the seed has run, when the Development Requester Selection screen loads, then all four active Requesters appear in the dropdown and the inactive Requester does not.
- **AC-02** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-03** Given a Requester is selected, when any application screen is displayed, then that Requester's name is visible in the application shell.
- **AC-04** Given Requester A is selected and their tickets are displayed, when the user changes to Requester B, then no ticket belonging to A remains visible and B's own tickets are loaded.
- **AC-05** Given a Requester is selected, when the page is reloaded, then the same Requester is still selected without re-choosing.
- **AC-06** Given the reference-data request fails, when the selection screen loads, then a safe failure state with a retry action is shown and no requester list is displayed.

### Ticket creation

- **AC-07** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-08** Given a Ticket has just been created, when its stored row is inspected, then `currentStatus` is `NEW` and `requesterId` equals the selected Requester's id.
- **AC-09** Given a generated Ticket Number, when it is inspected, then it matches `TKT-<YYYY>-<NNNNNN>` with the current year.
- **AC-10** Given several Create Ticket requests are issued concurrently, when all complete, then every returned Ticket Number is distinct.
- **AC-11** Given the Summary field is empty, when the Requester submits, then a validation message appears below the Summary field and no API request is sent.
- **AC-12** Given a Summary of fewer than 5 characters, when the Requester submits, then the server rejects it with 400 and a message identifying the `summary` field.
- **AC-13** Given a submission fails, when the error is displayed, then every value the Requester entered is still present in the form.
- **AC-14** Given a submission is in flight, when the Requester clicks submit again, then the control is disabled, a busy state is visible, and no second Ticket is created.
- **AC-15** Given the backend is unavailable, when the Requester submits, then a safe error message is shown that exposes no internal details, and the form values are preserved.
- **AC-16** Given a `categoryId` that refers to an inactive Category, when the Requester submits, then the server responds 400 with a field-level message, not 404.

### My Tickets

- **AC-17** Given Requester A owns tickets and Requester B owns others, when Requester B lists tickets, then no ticket owned by A appears in the response.
- **AC-18** Given a search term matching a Ticket Number, when the Requester searches, then that ticket is returned; the match is case-insensitive.
- **AC-19** Given a search term matching part of a Summary, when the Requester searches, then the matching tickets are returned.
- **AC-20** Given a Category filter is applied, when the list is returned, then every returned ticket has that Category.
- **AC-21** Given a sort field and order are supplied, when the list is returned, then the tickets are ordered accordingly.
- **AC-22** Given more tickets exist than one page holds, when page 2 is requested, then a disjoint set of tickets is returned and `total` reflects the full count.
- **AC-23** Given tickets share a sort value, when consecutive pages are requested, then no ticket appears on two pages and none is skipped.
- **AC-24** Given `pageSize=7`, when the list is requested, then the server responds 400 rather than silently using a different size.
- **AC-25** Given the Requester owns no tickets, when My Tickets loads, then the empty state invites them to create their first ticket.
- **AC-26** Given filters that match nothing, when the list is returned, then the no-results state is shown with a Clear Filters action, distinct from the empty state.
- **AC-27** Given the list request fails, when the screen renders, then a failure state with a retry action is shown.

### Ticket Detail

- **AC-28** Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned and the response status is 404.
- **AC-29** Given a Ticket the Requester owns, when its detail is opened, then Ticket Number, Ticket Date, Requester, Category, Related System, Summary, Requested Priority, Description, and Current Status are all displayed read-only.
- **AC-30** Given the Ticket Detail screen is displayed, when it is inspected, then it contains no Public Comments, Internal Notes, Actions Taken, IT Priority, or status-changing control.
- **AC-31** Given a Ticket id that does not exist, when it is requested, then the response is 404 with the same body shape as an unowned ticket.

### Attachments

- **AC-32** Given a permitted file under 5 MB, when the Requester uploads it to their own Ticket, then it is stored and appears in the Ticket's attachment list.
- **AC-33** Given a file larger than 5 MB, when it is uploaded, then the server responds 413 and no attachment row or file is created.
- **AC-34** Given a file of a type outside the permitted list, when it is uploaded, then the server responds 415 and no file remains on disk.
- **AC-35** Given a Ticket already has 5 active Attachments, when a sixth is uploaded, then the server responds 409.
- **AC-36** Given a Ticket has 5 active Attachments and one is removed, when a new Attachment is uploaded, then it succeeds.
- **AC-37** Given an active Attachment on an owned Ticket, when it is downloaded, then the response carries the stored content with the original filename in `Content-Disposition`.
- **AC-38** Given a removal reason, when the Requester removes an Attachment, then it is marked removed and its metadata, removal reason, and removal time remain visible.
- **AC-39** Given an Attachment has been removed, when its download is requested, then the response is 410 and no file content is returned.
- **AC-40** Given a removal request without a reason, when it is submitted, then the server responds 400.
- **AC-41** Given an already-removed Attachment, when removal is requested again, then the server responds 409.
- **AC-42** Given an Attachment on Requester A's Ticket, when Requester B requests its metadata, download, or removal, then every one of those responds 404.

### Identity, presentation, and accessibility

- **AC-43** Given no `X-Requester-Id` header, when a ticket endpoint is called, then the response is 401 with code `REQUESTER_HEADER_MISSING`.

- **AC-47** Given a keyboard-only user, when they traverse any form, then every control is reachable and the focus indicator is visible.

## 11. Assumptions and Decisions

Only choices not already fixed by the handout are recorded here.

| # | Decision | Rationale |
|---|---|---|
| D-01 | Requester identity travels in the `X-Requester-Id` header rather than a query parameter or body field. | It is the closest analogue to the `Authorization` header Lab 3 will use, so the swap is confined to one middleware. A query parameter would have to be threaded through every endpoint and every call site. |
| D-02 | Ownership failures return 404, not 403. | 403 confirms the resource exists, permitting enumeration of another Requester's ticket ids. Documented in BR-13 so a reviewer sees a decision rather than a bug. |
| D-03 | Ticket Numbers are allocated from a `TicketCounter` table inside the create transaction. | Gap-free, per-year, race-free without a retry loop, and deterministically testable. See §7. |
| D-04 | Attachment removal uses `PATCH /api/attachments/:id/remove`, not `DELETE`. | The resource is not deleted and remains addressable afterwards; `DELETE` would imply a subsequent 404. |
| D-05 | Attachments are stored on disk under `server/uploads/` with metadata in PostgreSQL, rather than as bytes in the database. | Keeps the database small and dumps fast. The cost — no atomic transaction spanning file and row — is accepted and mitigated by BR-40's orphan cleanup. |
| D-06 | Downloading uses `fetch` plus a blob URL in the client rather than a plain link. | A cross-origin anchor cannot carry the `X-Requester-Id` header, so a plain link could not pass the ownership check. |
| D-07 | Below the `md` breakpoint the ticket list renders as stacked cards rather than a horizontally scrolling table. | Satisfies "no horizontal page scrolling" while keeping every field readable, and produces clearer screenshot evidence than a clipped table. |
| D-08 | Summary is limited to 5–200 characters and Description to 10–5000. | The lower bounds reject non-descriptive placeholder input; 200 keeps a summary readable in one list column, and 5000 accommodates a pasted log excerpt without unbounded payloads. |
| D-09 | An unknown or inactive `categoryId` is a 400, not a 404. | The fault is in a submitted field value, so it belongs with the other field-level validation errors the form renders. |
| D-10 | `passwordHash` and `role` exist on `RequesterUser` from Lab 2, though unused. | Lab 3 then adds authentication to the existing identity table instead of migrating identities into a new one. |
| D-11 | Attachment type checking uses extension plus declared MIME type, without magic-byte inspection. | Proportionate to the sprint. Recorded as a known limitation in tests.md rather than left as a silent gap. |
| D-12 | `GET /api/tickets` is the only endpoint with a response envelope; reference-data endpoints return bare arrays. | Only the ticket list needs pagination metadata, and `GET /api/categories` must keep the Lab 1 response shape its existing test asserts. |
| D-13 | Server test files run sequentially (`fileParallelism: false`) against the shared development database, and each Lab 2 suite creates and cleans up its own Requester rows. | Four suites mutating one database in parallel interfere; truncating shared reference tables would break the Lab 1 test that asserts Category ids 1–4. |
